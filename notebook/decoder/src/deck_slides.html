Prefill once, then decode one token at a time

A decoder reads the prompt and produces text one token after another, each new token fed back in as input.

Prefill: all prompt tokens go through together. Decode: every later step pushes one token through every layer.

T = tokens so far (prompt + generated), growing by one per step · d = model width (4096 for Llama-3-8B) · h query heads · kvh key/value heads (8 for Llama-3-8B).

A token cannot look at the future

The model is trained to predict the next token, so seeing it would be cheating: token t attends only to tokens 0 … t.

S becomes a lower triangle: the cells above the diagonal are set to −∞ before the softmax and get probability 0.

A causal prefill does about half the attention work of an encoder on the same tokens.

Watch it grow

Step 1 is the prefill: the prompt's triangle of S. Every later step adds one row to S, one row to each cache, one output — checked against a full causal recompute.

The KV cache: why the past can be kept

Because of the mask, a token's K, V and output depend only on itself and earlier tokens. A later token changes none of them.

So they are computed once and kept. A decode step computes K and V for the new token only, appends them, and reads the rest back.

In an encoder there is no such choice: every token sees every token, so a new one changes all earlier outputs.

Cache on or off: same outputs, different work

Switch the cache off and every step recomputes the whole sequence. The outputs are identical — the check passes either way — but the work grows with T² instead of T.

Fewer key/value heads: a smaller cache

The cache holds K and V for every token, layer and KV head, so models share each K/V head among several query heads (grouped-query attention). Same arithmetic, a smaller cache.

One decode step: everything is memory-bound

Llama-3-8B, one new token at context 4096, on A100. Every projection is a matrix-vector product: each weight read once, used once — far below the ridge point. The time is the time to stream the weights.

Longer context: the cache takes over

Weights cost the same every step; every new token reads all earlier K and V. At 32k tokens the cache rivals the weights.

Batch: shared weights, private caches

Many users at once make every projection [B, d] × [d, d]: weights read once, used B times. Each sequence keeps its own cache, so batching multiplies the cache reads instead of sharing them.
