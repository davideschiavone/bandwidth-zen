The names we use everywhere

i walks over M: rows of A and of C

j walks over N: columns of B and of C

k walks over K: columns of A = rows of B. C has no k: it gets summed away.

C[i][j] += A[i][k] * B[k][j]

Pale green = unfinished C value (some of its 4 terms). Solid green = finished. A glowing outline = the operand that stays put.

The running example

Small whole numbers, so every step can be checked by hand.

Each C value is a sum of K = 4 products.

16 values × 4 products = 64 multiplies.

The first product of each value is just stored, the other 3 are added: 48 additions.

Every animation ends with the same C and checks it against A @ B.

The loop you already know

What just happened

Each C value was started, finished and never visited again.

During the whole k loop the running sum sat in one register. A and B values streamed past it.

"One dot product per C value" is the inner-product form.

Hardware names a loop after what stays put. Here C, the output, stays put: output-stationary (os).

The one rule behind every name

Each operand uses two of the three indices: A[i][k], B[k][j], C[i][j].

The innermost loop changes one index every step. The two operands that contain it change. The third one stays put.

Where the unfinished sums wait

Outside the inner-product form, a C value gets one of its 4 terms per visit and stays pale until the last one.

Between visits it waits in one place and is added to at many moments.

This is accumulating over time.

Tiling: the same thing, in chunks

Cut each 4×4 into four 2×2 blocks.

Treat each block as one "number" and each * as a small matrix product.

Block indices mt, nt, kt, each 0 or 1: a 2 × 2 × 2 grid of 8 block products.

C[mt,nt] = A[mt,0] @ B[0,nt] + A[mt,1] @ B[1,nt] — the textbook formula with blocks.

Three sizes of one step

The loops never change. The hardware decides how many of them happen at once.

CPU core: scalar × scalar, 1 multiply.

In-memory-compute array: vector × matrix, a row of A through a block of B that is stored in the memory cells.

GPU tensor core: matrix × matrix, a block of A times a block of B.

Four cores: how to read the picture

Top — the matrices. Blocks being read right now are lit, and a tag like c2 says which core is reading them. A glowing block is kept inside a core.

Middle — the chip. One box per core, showing the three blocks it touches in this step: what it keeps, what it gets, and the C block it adds into.

Bottom — the timeline. One row per core, one column per step. A bar is one tile of work; it fills up as the core works through it. Hatched = the core has nothing to do.

Every step, every busy core does one 2×2 block product (8 multiplies) at the same time.

Four cores, one product

Naming it: grid and sweep

Two of the three block loops were shared out: each core got one combination, and all cores ran at the same time (the rows of the timeline). That is the tile grid.

The third loop ran in order inside each core (the columns inside one bar). That is the sweep.

os: grid mt × nt, sweep kt  ·  ws: grid kt × nt, sweep mt  ·  is: grid mt × kt, sweep nt

The operand that stays put inside each core is the one the sweep does not index — the same rule as before, one level up.

More tiles than cores: waves

Cut C into 8 tiles of 1×2. Each tile is swept over K in 2 steps. With 3 cores the tiles are handed out in rounds; try other core counts.

When k is on the grid

Now the cores keep blocks of B (ws) or A (is). Two cores make pieces of the same C block — watch the “2×” cells, then the extra combine step.

Zoom on one output: where the additions happen

os runs out of tiles

In os one core owns one output block and sweeps all of K inside it. So the number of tiles is the number of output blocks: here 4 (a 4×4 C in 2×2 blocks), however many cores there are.

Split-K: cut the sweep into pieces

Cut each block's K sweep into P pieces: with P = 2, k 0–1 and k 2–3.

The unit of work becomes (output block, piece of K): 4 blocks × 2 pieces = 8 tiles, so 8 cores can work at once.

Each tile gives only part of the sum: a pale block. It must wait somewhere until the other pieces are done, so it goes out to memory.

A second pass reads the pieces back and adds them into the final C.

Same 64 multiplies and 48 additions. What is new: (P−1)·16 of the additions happen in pass 2, and 2·P·16 values go through memory (P·16 written, P·16 read back).

Split-K, step by step

The other way to 8 tiles: ws

ws also puts K to work in parallel, but it puts every K-slice on the grid: 4 slices × 2 column blocks = 8 tiles. No memory trip — the pieces meet across cores.

Both buy parallel work by cutting K. Split-K cuts it into big pieces and pays with memory traffic. ws puts every K-slice on the grid and pays with additions across cores.

A core that stores several blocks of B

An in-memory-compute core keeps B in its cells (ws). Some can store a few blocks at once: weight sets, or slots.

It computes with one slot at a time. The others only hold data.

Writing a block into a slot takes time: here 2 steps. The extra slots can be used in two ways:

(a) hide the loading: fill the next slot while computing with this one.
(b) keep K in one place: put successive K-pieces of the same column in the slots.

Tiny version: 2 slots of a 2×2 block. Real (your figures): Axelera Metis has 4 cores, each holding 4 weight sets of 512×512 bytes and computing with one at a time. 4 × 512 × 512 B = 1 MiB per core, which matches the 1 MiB of compute memory per core that Axelera publishes.

More cores than columns: K-groups

B has only 2 column blocks but there are 4 cores. Cut K into 4 slices, give each core a group of them in its slots: it sums its group over time, and only one partial per core meets the others at the end. With 2 per core, 2 pieces per C value instead of 4.

Every form, same answer

Loop order decides what stays put and when a C value is finished.

Tiling applies the same rule to blocks.

Hardware decides how big one step is.

Parallelism decides whether the K-sum happens over time or across space.

The arithmetic never changes: 64 multiplies, 48 additions.
